# ApplyTrack Agent Guide

This file is the operating guide for AI coding agents working on ApplyTrack. Use it together with `README.md` and `PRODUCT.md`.

## Product Context

ApplyTrack is a job application tracker for job seekers managing applications, interviews, follow-ups, offers, and rejections. It is a product UI, not a marketing site. Prioritize task clarity, responsive behavior, privacy, and familiar app affordances over decorative flourishes.

Core product principles:

- Keep the next action visible.
- Make dense application data scannable before making it decorative.
- Use standard product affordances for forms, navigation, sorting, filtering, destructive actions, and account settings.
- Adapt structure across screen sizes instead of simply shrinking desktop UI.
- Preserve user trust around private job-search data and account recovery.

## Tech Stack

- React 19 with Vite
- Supabase Auth, Database, RLS, and Edge Functions
- Recharts for progress visualization
- `xlsx` for Excel imports
- Resend for password recovery delivery

## Environment And Secrets

Use `.env.example` for public placeholders only:

```env
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=your-publishable-key
```

Do not commit `.env.local`, Supabase service role keys, Resend API keys, or function `.env` files. `.gitignore` already excludes `*.local` and `supabase/functions/.env`.

The Supabase publishable key is expected in browser code. Service role access belongs only in server-side contexts such as Edge Functions.

## Routing

The app uses lightweight hash routing in `src/utils/routes.js`.

- Routes look like `#/dashboard`, `#/profile`, `#/progress`, `#/import`, `#/applications/new`, and `#/applications/:id/edit`.
- Use `navigate('/path')` instead of writing `window.location.hash` directly.
- `App.jsx` owns route selection and passes shared page navigation props to pages.

Do not add a routing library unless there is a clear need and the change is intentionally scoped.

## Authentication Model

ApplyTrack asks users for a username and password. Supabase Auth still requires an email, so `src/api/auth.js` generates an internal email from the username and Supabase project host.

Important details:

- Internal auth email format is generated by `createAuthEmail(username)`.
- The user's real optional recovery email is stored in `user_metadata.profileEmail`.
- Profile email UI should call this a "Recovery email", not the primary Supabase Auth email.
- Do not show generated Supabase/internal auth email values to the user.

Session persistence is configured in `src/lib/supabase.js` with browser-session cookies so users stay signed in across tabs but not after fully closing the browser session. Be careful when changing this behavior.

## Password Recovery

Password recovery uses the public Edge Function at `supabase/functions/request-password-reset/index.ts`.

The function:

- Accepts a recovery email.
- Searches `user_metadata.profileEmail`.
- Generates a Supabase recovery link using server-side credentials.
- Sends the email through Resend.
- Returns a neutral public message so the app does not reveal whether an account exists.
- Includes simple in-memory rate limiting.

Keep public recovery responses neutral. If adding stronger abuse protection, prefer platform-level rate limiting, CAPTCHA, or logging rather than account-enumerating messages.

When changing the Edge Function, remind the user that it must be redeployed:

```powershell
npx supabase functions deploy request-password-reset
```

## Database Rules

The `applications` table is defined in `supabase/schema.sql`.

Key assumptions:

- Every application belongs to `user_id`.
- RLS is enabled.
- Select, insert, update, and delete policies are scoped by `auth.uid() = user_id`.
- `company` and `role` are required.
- `last_updated` is a user-facing date field; `updated_at` is a database timestamp maintained by trigger.

When adding fields, update all relevant places:

- `supabase/schema.sql`
- migration helper SQL, if needed
- `src/data/applications.js`
- `src/api/applications.js`
- add/edit form
- application card display
- Excel import mapping, if the field should import

## Application Data Behavior

Application normalization lives in `src/data/applications.js`.

Current behavior:

- New applications default `date` and `lastUpdated` to the local current date.
- Editing an application automatically updates `lastUpdated` to today's local date.
- Dashboard sorting defaults to latest applied date first.
- Users can sort by applied date or last updated date.
- Interview metrics use `interviewCount`, not only the `Interview` status.

Preserve local date handling. Avoid `toISOString().slice(0, 10)` for user-facing "today" because UTC can be off by one near midnight.

## UI And Design Conventions

This is a focused product workspace.

Follow these conventions:

- Keep controls familiar and explicit.
- Use buttons for actions, labels for inputs, and native inputs/selects where appropriate.
- Keep touch targets at least 44px on mobile.
- Preserve visible focus states.
- Avoid decorative icons that obscure meaning.
- Avoid landing-page style hero sections inside authenticated views.
- Avoid hiding core functionality on mobile.
- Use compact but readable cards for application data.
- Use clear confirmation for destructive actions.

Visual system:

- Base styles live in `src/App.css`.
- The current theme and responsive override layer live in `src/styles/theme.css`.
- Keep future responsive fixes in the theme layer unless a base style truly belongs in `App.css`.
- `PRODUCT.md` captures the product direction and should guide design decisions.

Responsive expectations:

- Dashboard must work at phone, tablet, and desktop widths.
- Sidebar becomes a top mobile navigation area on narrower screens.
- Dashboard filters and pagination stack on phone.
- Application cards become single-column on phone.
- Progress chart uses compact labels/margins on phone.
- Progress calendar becomes a single-column weekly list on phone.

## Excel Import

Excel parsing lives in `src/utils/excelImport.js`; UI lives in `src/components/ExcelImportPanel.jsx`.

Import behavior:

- Supports `.xlsx` and `.xls`.
- Reads the first sheet.
- Requires at least company and role.
- Shows a preview and lets users choose rows before importing.
- Infers interview count from an interview stage when possible.

Keep import failure messages practical and non-technical.

## Accessibility Notes

Target WCAG AA basics:

- Sufficient contrast for text and controls.
- Keyboard-operable controls.
- Visible focus styles, including custom check indicators.
- Semantic headings, labels, buttons, and navigation.
- No color-only status communication.
- Respect reduced motion.

When creating custom controls, make sure the native input or button semantics remain available to assistive technology.
